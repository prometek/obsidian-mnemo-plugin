# Code Standards — obsidian-mnemo-plugin

## General

- Keep modules small and single-responsibility.
- No mixed concerns in a single component or module — delegate business logic to a service layer.
- Separate I/O from pure logic: pure logic must be testable without filesystem, network, or Obsidian API.
- Composition over inheritance.
- Fix root causes, never stack workarounds.
- No `any`, `@ts-ignore`, or empty `catch {}` — unless justified in a comment.
- Validate all external input (user settings, IPC responses, file content) at system boundaries before it reaches business logic.
- Errors typed explicitly — never raw strings or magic codes.
- No magic numbers: extract named constants.
- Comments only for non-obvious *why*, never for *what* — code must be self-explanatory.
- Explicit naming over short: no `tmp`, `data2`, `obj`, `foo` in production code.
- Functions over ~50 lines or components over ~150 lines: suspect single-responsibility violation.
- No logs containing PII or secrets.

## TypeScript

- Strict mode enabled (`"strict": true` in `tsconfig.json`).
- Prefer `interface` for object shapes used as contracts; `type` for unions, intersections, and aliases.
- No `as` casts unless unavoidable — if needed, add a comment explaining why.
- No `any` — use `unknown` and narrow explicitly.
- No `non-null assertion` (`!`) without a justifying comment.
- Explicit return types on all exported functions.
- Use `const` by default; `let` only when reassignment is necessary.
- Avoid mutable shared state — prefer passing data explicitly.
- ESLint + Prettier for lint and format (configured in `.eslintrc.json` and `.prettierrc`).
- Prettier is the source of truth for formatting; ESLint does not reformat.
- `tsc --noEmit` run in CI (type check, not build).

## Obsidian Plugin

- Extend `Plugin` class for the main entry point (`main.ts`).
- All plugin lifecycle logic in `onload()` and `onunload()` — clean up every registered resource in `onunload()` (event listeners, commands, intervals, leaf references).
- Use the Obsidian API exclusively for vault and UI operations — no raw filesystem access outside of what the API exposes.
- Settings stored via `loadData()` / `saveData()` (Obsidian API) in `data.json` — never write settings to a custom path.
- Define a typed `Settings` interface; define `DEFAULT_SETTINGS` as a const; merge with `Object.assign({}, DEFAULT_SETTINGS, await this.loadData())` on load.
- Register commands with `this.addCommand()` — provide both `id` (kebab-case) and `name` (human-readable).
- Register settings tab with `this.addSettingTab()` — implement as a separate `PluginSettingTab` subclass.
- No direct DOM manipulation outside of Obsidian API methods or `MarkdownRenderer` — use `containerEl.createEl()` and related helpers.
- Build target: esbuild producing a single `main.js` at the repo root (standard Obsidian plugin layout).
- Never import from `obsidian` in unit-tested pure-logic modules — keep them framework-agnostic to enable Vitest without mocking the Obsidian API.

### Communication with obsidian-mnemo (SSE)

- `obsidian-mnemo` runs as an MCP server over **SSE transport** on `http://127.0.0.1:8765`.
- Plugin spawns the server process at `onload()` via `child_process.spawn('obsidian-mnemo', ['--vault', vaultPath])` and kills it at `onunload()`.
- Before spawning, check if port 8765 is already in use — if so, reuse the running instance (allows external MCP clients to share the same server).
- Bearer token read from `~/.obsidian-mnemo/config.json` (auto-generated by the server on first run, `chmod 600`).
- All HTTP calls to the server include `Authorization: Bearer <token>` — never store the token in `data.json` or in the plugin settings UI.
- All server calls go through a single `MnemoClient` service class (`src/services/mnemoClient.ts`) — no raw `fetch` to the server elsewhere in the codebase.
- `MnemoClient` must handle: server not yet ready (retry with backoff), server process crashed (attempt respawn once, surface error to user), token file missing (surface actionable error).
- Side effect of SSE: while Obsidian is running with the plugin active, the server is accessible to any MCP client on the machine (Claude Desktop, Cursor, etc.) — this is intentional and documented behaviour.

## Tests

- Vitest for unit tests.
- Test all pure logic (spaced-repetition algorithms, data transformations, settings merging) without mocking the Obsidian API.
- Integration tests that require the Obsidian API: use minimal stubs, document what is stubbed and why.
- Minimum coverage: happy path + one error case per public function.
- Tests must be deterministic: no dependency on execution order, no real timers (`vi.useFakeTimers()`), no external network calls.

## File Organization

### TypeScript

```
src/
  main.ts               # Plugin entry point (extends Plugin)
  settings.ts           # Settings interface, DEFAULT_SETTINGS, SettingTab
  commands/             # One file per command group
  services/
    mnemoClient.ts      # Single MnemoClient class — all HTTP calls to obsidian-mnemo
    serverManager.ts    # Spawn / health-check / kill the obsidian-mnemo process
  ui/                   # Modals, views, custom UI components
  utils/                # Pure utility functions
tests/
  unit/                 # Tests for services/ and utils/
main.js                 # Built output (esbuild)
manifest.json           # Obsidian plugin manifest
```

## Git & CI

### Conventional Commits

- Format: `type(scope?): description`.
- Types: `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `perf`, `build`, `ci`, `style`, `revert`.
- Description: present tense, imperative, lowercase, no trailing period.
- Breaking changes: `feat!:` or footer `BREAKING CHANGE:`.

### Branches & PR

- Main branch: `main`.
- Work branches: `feat/...`, `fix/...`, `chore/...`, `refactor/...`.
- No direct commits to `main` — everything via Pull Request.
- PR titles follow Conventional Commit format (used for squash merge and changelog).

### Pre-commit hooks

- Use `pre-commit` framework (`.pre-commit-config.yaml` committed at root).
- After clone: `pre-commit install && pre-commit install --hook-type commit-msg`.

Hooks included:

- **ESLint auto-fix** — fix auto-correctable issues, block on the rest.
- **Prettier format** — auto-fix and re-stage.
- **Secret detection** — `gitleaks` or `detect-secrets`, blocks commit on hit.
- **Conventional commits** — `commit-msg` hook (commitlint or equivalent).
- **Large files** — block files > 500 KB.

Hooks excluded (too slow, run in CI only): `tsc --noEmit`, Vitest.

### GitHub Actions

- CI triggered on PR and push to `main`.
- Mandatory blocking steps:
  - ESLint lint check.
  - Prettier format check.
  - `tsc --noEmit` type check.
  - Vitest unit tests.
  - esbuild production build.
- No merge if any step fails.
- Cache `node_modules` (by `package-lock.json` hash) to speed up runs.

## Secrets Management

- No secrets in plaintext in the repo or in code.
- API keys, tokens, or credentials needed at runtime: loaded from environment variables, never hardcoded.
- Obsidian plugin settings (`data.json`) must not contain the `obsidian-mnemo` bearer token — read it from `~/.obsidian-mnemo/config.json` at runtime.
- `.gitignore` must include `data.json` if it can contain sensitive values.
- Secret detection hook (`gitleaks`) runs on every commit.
